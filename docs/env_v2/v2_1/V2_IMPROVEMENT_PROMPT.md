# Prompt: improvement plan for the FinPersona-Bench synthetic market environment (v2 → v2.1)

## Context

FinPersona-Bench evaluates whether LLM trading agents keep to a persona's mandate over a multi-day market run. The market is synthetic. The original environment (v1, frozen at `envs/v1/synthetic_market_v1.py`, documented in `docs/env_v2/v1_baseline/E0_SUMMARY.md` and `docs/env_v2/v1_baseline/E0_V1_GENERATOR_SPEC.md`) had structural defects: valuation fields that inverted to the hidden value, phases fixed to the calendar, no volatility clustering, label-driven observables, a 100 %-cash start, stipulated targets, and a prompt that did not match the paper.

We rebuilt it as v2 following `docs/FinPersona-Bench_Synthetic_Environment_v2_Plan_Aug2026.docx` (also `.pdf`). v2 is the code in `envs/v2/*.py`, `envs/synthetic_market.py`, `envs/v2/params/*.json`, with the harness in `agent/`, `simulation/`, `experiments/arms_v2.py`, the evaluation layer in `evaluation/`, tools in `tools/`, tests in `tests/`. Its documentation is in `docs/env_v2/` (`README.md`, `E1_V2_GENERATOR_SPEC.md`, `CALIBRATION_REPORT.md`, `DECISION_LOG.md`, `DECISIONS_13_1.md`, `PREREGISTRATION.md`, `PREREGISTRATION_AMENDMENTS.md`, `IO_CONTRACT.md`, `E1_E4_STATUS.md`, `PILOT_NOTES.md`), with generated results in `docs/env_v2/generated/` (checklists v1/v2, leakage audits v1/v2, sensitivities, hazard calibration, FW J-profile, observables oracle, pilot reports, Table 2). Background research is in `docs/env_research/*.md` (targets, design, time-series, plan coherence and fact-check notes) and earlier review rounds in `docs/cycle1_reviews/`, `docs/cycle2_reviews/`, `docs/SYNTHETIC_MARKET_AUDIT.html`. A slide deck and speaker script describing v2 are in `docs/env_v2/slides/`.

v2 is a clear improvement on v1 but it is not robust. Three independent reviews (`docs/env_v2/reviews/review_A_parameter_provenance.md`, `review_B_claims_vs_evidence.md`, `review_C_methodology_robustness.md`) and the consolidated list `docs/env_v2/reviews/V2_WEAKNESSES.md` identify: about 200 numeric choices of which only a dozen trace to published statistics; a fixed start price that acts as an answer key; a Franke-Westerhoff engine whose switching is inert because of a units factor; a flat-market control biased cheap by jumps; fields that leak the hidden state once the start-price anchor is removed; an implied-volatility phase clock and look-ahead; a calendar that is still a phase clock in the runs actually executed; checklist thresholds without empirical reference distributions or power analysis; claims on the slides that the audits contradict; an analyst-error bug; wrong sensitivity counts; mislabelled regret normalisation; an ill-posed day-1 gate; and no generator-parameter sensitivity run through the LLM grid. Read all of these before doing anything.

## What we want from you

An improvement plan that takes v2 to a robust version (same environment, same repository, call it v2.1) and fixes every item in `V2_WEAKNESSES.md`, then execution of that plan phase by phase. First deliver the plan as a document for review, with no code changes. Only after the plan is approved, execute one phase at a time, and stop for review at the end of each phase.

## Hard rules

1. **Do not assume anything.** Every parameter, range, threshold, baseline and design choice must be justified by published finance literature (reputable, citable, with the specific statistic and where it comes from) and then fitted or tested on data or by experiment before it is adopted. "It was in the plan", "it is conventional", "it seems reasonable" and "it made the checklist pass" are not justifications.
2. **No arbitrary suggestions.** If the literature gives a range, present the range with sources, then run the experiment (sweep, fit, variability analysis) that narrows it, and decide from the results. If it cannot be decided from evidence, say so and present the options with their consequences; do not pick one by preference.
3. **Research, experiment, test, then decide, in that order.** Every phase must contain: a literature review with sources; an experimental design written before the runs (seeds, horizons, statistics, pass criteria with a power analysis); the runs; the decision with the evidence; regression tests that lock the decision in; documentation.
4. **Pre-registration discipline.** Thresholds and criteria are written before the data are seen and are not moved afterwards. If a criterion turns out to be wrong, say that and re-derive it from an empirical reference distribution in a separate, documented step, and report the result under both the old and the new criterion. Label every parameter that is tuned to a criterion as a calibration target, not a validation.
5. **Report failures as failures.** No claim in any document or slide may be stronger than the evidence behind it. Every number is reported with its sample size (seeds, horizon, paths) and an interval where one can be computed. Before/after comparisons must be like for like (same window, same estimator, same seed count).
6. **Verify before you cite the repository's own documents.** Several existing numbers are stale or wrong (see `V2_WEAKNESSES.md` part 6). Recompute anything you rely on.
7. **Scale of evidence.** Use enough seeds and long enough horizons for the statistic in question, chosen by a power analysis, not by habit. Run generator sensitivities through the LLM harness for the parameters that drive results, not only through the checklist. Parallelise API calls (10 to 15 concurrent); costs are acceptable, but propose the grid and its cost before running anything against paid APIs; keys are in `.env`, never print them.
8. **Git.** All work stays on `main`; do not create branches. **Do not commit, amend, reset, stash or push unless the user explicitly asks in that message.** Leave changes in the working tree and list them. Do not modify the frozen v1 code or the plan document. Use the scratchpad directory for temporary files.
9. **Keep the decision trail.** Every decision goes in `docs/env_v2/decisions/DECISION_LOG.md` with the evidence, the alternatives considered and why they were rejected; every deviation from the plan in `PREREGISTRATION_AMENDMENTS.md`.
10. When a step is blocked on a decision only the user can make, do everything that does not depend on it, then ask with the options and evidence laid out.

## Modules and phases (proposed; refine in the plan)

Each phase ends with a written report and waits for approval.

- **Phase 0. Verification and freeze.** Reproduce every finding in the three reviews; fix outright bugs (analyst-error scaling, sensitivity counts, regret normalisation labels, day-1 gate input, silent parameter overrides, stale documents); add hash-freezing over `envs/v2/**` and `params/*.json` and statistical regression tests (E[x] in flat, error sds, IV continuity, fundamentalist-share distribution); make the test suite clean. No design changes.
- **Phase 1. Value and price structure.** Start-price randomisation; the value process (drift, volatility, tails) fitted to data with sources; where jumps belong; burn-in. Re-run the leakage audits with a level-free price control and re-state what is and is not inferable.
- **Phase 2. Mispricing engine.** Resolve the Franke-Westerhoff units question against the original paper; decide between a working FW and an honest AR(1); estimate the persistence from firm-level data with a proper method (multi-start SMM with persistence-carrying moments, 100+ stocks, several periods) and report a bias-corrected half-life; sweep persistence through the checklist and the LLM harness.
- **Phase 3. Volatility.** GJR-GARCH-t parameters fitted per stock on a stated dataset; jump rate and size from data; phase variance multipliers from regime-conditional evidence; an implied-volatility construction that is not a phase step and has no look-ahead.
- **Phase 4. Events, schedule and controls.** Crash and bubble durations, depths, discounts and hazard from historical episodes (Mishkin & White 2002, Barro & Ursua 2017, Greenwood, Shleifer & You 2019, LPPLS fits); the sustained-bull control on the same mispricing process as the flat market, with published selection effects; the error-correction gains justified or replaced; orderings run in the grid; the calendar removed as a clock.
- **Phase 5. Observables.** Earnings, P/E multiple range, dividends, analyst error, sentiment, volume and technicals each anchored to a stated empirical source and designed so that no field is a deterministic function of the hidden state; audited for leakage with the level-free control and an onset-detection test.
- **Phase 6. Audits and checklist methodology.** Every checklist statistic given an empirical reference distribution from real 200-day windows of large-cap stocks; per-item power analysis; seeds and horizons set accordingly; extended L1 candidate set; L2/L2b gates derived, not stated; leakage reported with percentiles and intervals.
- **Phase 7. Targets, action and metrics.** Resolvability threshold derived; regret decomposed into band adherence and directional agreement, with correct floor and ceiling; bands checked for consistency with the environment's own risk and return, dividends paid or the field removed; the day-1 gate re-specified; baselines rebuilt on each cell's actual path.
- **Phase 8. Harness and statistics.** Stateful-arm covariates and token budgets corrected; context length as a swept factor; mixed-model specification, clustering and multiplicity fixed; salience shares identified or dropped; a power analysis for the main grid.
- **Phase 9. Sensitivity through the LLM harness.** The six or so generator parameters that drive results swept through a small LLM grid to show which conclusions are robust.
- **Phase 10. Documentation, slides and script.** Every document, the deck (`docs/env_v2/slides/`) and the speaker script corrected to the verified numbers, with sample sizes and calibration labels on every slide.

The plan document only: for each phase, the weaknesses it addresses (by number from `V2_WEAKNESSES.md`), the literature to be consulted, the experiments with their design, the decision rules, the tests, the estimated compute and API cost, and what could block it. Do not change code, do not run paid APIs, do not commit.
