# Independent review of `V2_1_IMPROVEMENT_PLAN.docx` (26 Aug 2026)

Reviewer: Claude (this session), reading the plan cold against the three v2 reviews, `V2_WEAKNESSES.md`, the prompt, and the current working tree. No files other than this one were written.

## Verdict

The plan can be trusted as a plan. It is consistent with the reviews, it re-ran the headline findings itself and got the same numbers I got independently (flat-market x mean −0.100, fundamentalist share > 0.99 on 98 % of days, the "price vs 100" rule at 0.005–0.014 regret, analyst sd 0.35, sensitivity footers wrong in five files), it maps every one of the 74 weakness items to exactly one closing phase, it is honest about the biggest constraint (no CRSP/Compustat/OptionMetrics/IBES access, so several parameters can only be literature-anchored plus sensitivity), it separates fitted values from calibration targets from team decisions (LIT/FIT/CAL/DESIGN), it writes pre-registrations before runs and states power rules, and it lists twelve decisions that are the team's rather than deciding them silently. The protocol in Section 1 is the right one.

It should not be executed as written without the eleven adjustments below. None of them is a flaw in the direction of the plan; they are places where it either embeds a design decision that should be yours, chooses a fix that has a cleaner alternative, relies on facts it could not verify, or leaves out a stopping rule.

## Pointers before acting on it

1. **Start-price fix: consider normalising the price, not randomising the level.** E1.1 draws the start price log-uniformly from a P5–P95 range of real share prices. That removes the answer key but introduces a new nuisance for the LLM: a "$18 stock" and a "$420 stock" may be treated differently by a language model, and that magnitude effect would enter every contrast. A cleaner alternative is to keep the rendered start price at 100 and set V_1 = 100·exp(−x_1), i.e. normalise the price rather than the value. Then log(P_t/100) = (x_t − x_1) + (log V_t − log V_1), which reveals changes but not the level of mispricing, and the day-1 price carries no information. Pre-register both (normalise-price vs random-level) in E1.1, run the level-based attacker on both, and log the rendered level as a covariate in whichever is adopted. Note that the analyst field and EPS × k still reveal V_1 under either option; that is Phase 5's job, and Phase 1 should say so rather than claim the anchor is closed.

2. **Two design changes are decided in the plan that should be D-items.** (a) E4.5 puts the sustained bull on the same mispricing process as the flat market and removes the x-band. That restores the v2 plan's d_t = 0, but it also changes what the control is: with a 150-day half-life and sd 0.13, a "sustained bull" run can carry −30 % mispricing for months, so the scenario becomes "flat market plus rising value", not "rising value without a bubble". The anchoring was added in v2 precisely because more than half of unforced draws violated the band. Whether the control's purpose survives without the band is your call; add it as D-item. (b) E5.5 sets the sentiment's valuation loading to zero by default. That is defensible (Tetlock is sentiment-to-returns) but it is a design choice with consequences for the non-price leakage result; list it with the alternatives.

3. **Add a go/no-go checkpoint after Phase 6.** The plan's own D3 says the fitted σ_V may be much larger than 0.006, which makes mispricing hard to infer from price; Phase 5 may strip the fields of most of their information; Phase 7 measures whether each run is a one-shot side call. After those, the benchmark may be either trivially solvable or unplayable by a memoryless agent. The plan should state, before Phase 1 starts, the criterion under which the environment is still meaningful (for example: the mandate oracle beats every trivial policy by a pre-registered margin, the level-free observables oracle sits between the trivial policies and the oracle, and the median number of oracle switches per run is at least k), and what happens if it is not met.

4. **Every citation marked "(to verify)" must be verified before its number is used, and the phase report must say which were read.** The plan promises this in Section 1. Enforce it: a phase report that cites a statistic from memory ("recalled Table 3") is not acceptable under the hard rules, and several literature bullets (Vuolteenaho's cash-flow share, Cohen-Polk-Vuolteenaho's 75–80 %, Bartram-Grinblatt's decay, Lintner's 0.3, Brav-Lehavy's 28 %, Karpoff's table) are currently recalled, not read.

5. **Facts stated as checked "today" that you should re-check before approving budgets or timelines:** the API prices (GPT-5 mini "$0.125/$1.00 after July 2026 cuts", Claude Sonnet 5 $2/$10, Opus 5 $5/$25, Haiku 4.5 $1/$5, Gemini Flash $0.30/$2.50); the FW 2012 PDF being reachable at the Bamberg URL; yfinance retrieval rates; EDGAR company-facts coverage. I could not verify the prices; treat every cost figure as an estimate until the provider pages are read.

6. **Survivorship is bigger than the plan's mitigation suggests.** Building the universe from historical S&P 500 constituents helps, but any name that delisted before yfinance's coverage is lost, and those are exactly the crashes, tails and drawdowns Phases 3, 4 and 6 need. The plan reports survivor-sample statistics beside literature full-universe values; that is the best available, but the reference distributions for checklist items 2, 3, 8 and 20 and the crash-episode tables will be biased toward calmer stocks. Say so on the slides, and keep D1 (obtain WRDS access through the institution) as a real option, not a formality.

7. **The θ derivation ties "correct" to a fitted attacker.** E7.1's default θ_info is the mispricing at which the level-free surrogate reaches 80 % sign accuracy. That makes the definition of a right answer depend on a model that changes whenever the fields change (Phase 5) or the surrogate improves. It is a reasonable primary derivation, but the cost-based θ_cost is the one that does not move with the attacker; consider making the two co-primary and reporting both throughout rather than one default and one sensitivity.

8. **Effort and calendar time are missing.** Each phase lists compute hours (minutes to a few hours) but not the analyst effort: reading and transcribing the literature, building the EDGAR panel, writing twelve pre-registrations, three different event formulations, a full SMM rebuild, a statistics-track re-specification with simulation checks, and a claims ledger with a drift test. That is weeks of work, not the hours the compute column implies. Ask for a per-phase effort estimate and decide which phases can run in parallel (0, then 1+2+3 share the data panel; 4 and 5 can proceed in parallel after 3; 6 needs 1–5; 7 needs 5–6; 8 is independent of 1–7 except for the pilot).

9. **A minimal path exists and should be named.** If time is short, the order that changes the story fastest is: Phase 0 (bugs, freeze), E1.1 + E1.6 (start-price fix and level-free audit), E2.1 (FW units), E5.7 (field ablation), Phase 7's E7.2 (regret decomposition and normalisation fix), then Phase 10 (honest deck). That six-step subset closes the seven headline items and produces a defensible v2.0.1 before the fitting programme starts. The plan should say whether it recommends the full programme or the minimal path first.

10. **Some Phase 0 changes are not zero-design.** Restricting the day-1 gate to common-start cells (0.2), renaming the engine, and making the IV/analyst tests strict xfails are fine; but "regenerate the sensitivity footers" and "correct every 50-seed claim" will change numbers on the slides that are currently being presented. Phase 0 should produce a one-page "corrections to the current deck" note immediately, rather than waiting for Phase 10, so that nobody presents the wrong sensitivity counts or the "nothing re-tuned" tile in the meantime.

11. **Small things.** (a) E1.1's "V_1 = start price still holds" contradicts pointer 1 if the normalise-price option is chosen; make the two consistent. (b) E3.5's IV filter is run on observed returns only, which is right, but the premium π_t as a function of the filter's variance level will still rise at a panic onset (legitimately, through returns); the onset audit should compare IV against realised variance from the same filter so that the test is fair. (c) E4.3 derives the hazard slope from GSY's 2-year crash probabilities; the mapping to a daily hazard over a 150-day mania needs a stated horizon assumption, which the plan should write down. (d) Table 4's "Sentiment valuation loading: 0 / half / full Baker–Wurgler-sized" needs a stated definition of "full" before it is a level. (e) `V2_IMPROVEMENT_PROMPT.md` paths need updating to the new tree.
